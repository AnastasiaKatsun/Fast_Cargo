#**1. Выгоды бизнеса**
* **Масштабирование x10 без деградации SLA.** Переход на микросервисы и асинхронную шину позволит обрабатывать до 500 тыс. отправлений/сутки и 3 000 RPS телематики без блокировки транзакций тяжёлыми отчётами.
* **Соответствие регуляторным требованиям.** Изоляция PII‑контура (ФЗ‑152) и платёжного сегмента (PCI DSS) снимает юридические риски и открывает доступ к контрактам холдинга.
* **Снижение стоимости простоя.** Устранение единой точки отказа (монолит + общая БД) и внедрение dual‑run сокращают потери выручки при инцидентах; доступность ядра ≥99,95% (4,4 часа недоступности в год).
* **Ускорение релизного цикла.** Разделение BFF и доменов позволяет командам релизить изменения независимо, сокращая цикл с >2 недель до daily‑деплоев.
* **Рост операционной эффективности.** Перенос отчётности в DWH и автоматизация EDI исключают ручные операции и аномалии (например, оплату без товара).


#**2. Базовая и целевая архитектура**

**AS‑IS (антипаттерн):** монолит с синхронными вызовами модулей и общей PostgreSQL; жёсткие связи между таблицами доменов; BFF как единая кодовая база для всех фронтендов; отсутствие изоляции платёжного и PII‑контуров. Главный антипаттерн — общая база данных как единая точка отказа, где тяжёлые отчёты блокируют транзакционные операции.

**TO‑BE (ключевые паттерны):**

* Событийно‑ориентированная микросервисная архитектура с Database‑per‑Service (отдельные БД для доменов Orders, Warehouse, Delivery, Billing и др.).
* Асинхронный обмен через шину событий (Kafka) с Transactional Outbox и идемпотентными консьюмерами; саги вместо распределённых транзакций.
* Изолированные контуры: PII‑vault (ПДн), Payment‑сервис (PCI DSS), телематика (MQTT → Kafka → Timescale/ClickHouse).
* Разделение BFF на независимые деплои (Web, Courier, Partner) с общей библиотекой контрактов.
* Аналитика в реальном времени через CDC (Debezium) без нагрузки на транзакционную БД.


#**3. Область применения**
**In‑scope:**

* Домены: Заказы, Склад, Доставка/Телематика, Финансы, Мастер‑данные.
* Контуры: PII‑vault, Payment‑сервис, EDI‑gateway, CRM‑read‑model.
* Слой интеграции: CDC‑пайплайн (Debezium → Kafka → Flink → DWH), MQTT‑шлюз для IoT.
* Инфраструктура: кластеры Kafka, ClickHouse/Timescale, Patroni для PostgreSQL, managed‑облако для эластичных компонентов.

**Out‑of‑scope:**

* Исходный код легаси‑монолита (запрещены правки, кроме конфигурации).
* Внутренние системы холдинга «Продукты с душой» (CRM, EDI, DWH) — только интеграция через контракты.
* Физическая логистика и автопарк (транспорт, водители, склады) — операционные процессы не меняются.
* Внешние платёжные провайдеры и банки — только сценарии интеграции (редирект, hosted fields).


#**4. Ограничения и допущения**
* **Сроки:** переходное решение (real‑time аналитика) — 3 месяца; полная миграция на микросервисы — 12 месяцев.
* **Бюджет:** CAPEX ограничен; приоритет — Open Source (Debezium, Kafka, Flink, EMQX) и managed‑сервисы для эластичных нагрузок.
* **ИБ:** соответствие ФЗ‑152 (изоляция ПДн, обезличивание в DWH), PCI DSS (PAN не попадает в контур Fast Cargo), ГОСТ Р 34.12‑2015 (шифрование), приказ ФСТЭК №21 (меры защиты).
* **Допущения:** наличие реплики PostgreSQL для CDC; возможность выделения отдельных сетевых сегментов для PCI/PII; готовность холдинга предоставить API‑контракты CRM/EDI/DWH.

#**6. Описание переходного состояния (real‑time аналитика ≤5 с)**
* **Паттерн:** CDC (Change Data Capture) через логическое декодирование WAL‑логов PostgreSQL с использованием Debezium (pgoutput) без нагрузки на транзакционную БД.

* **Техническая реализация:**

* **Источник:** PostgreSQL (реплика) с replication slot на standby; pgoutput для логического декодирования без дополнительных расширений.
* **Транспорт:** Debezium → Kafka (Avro + Schema Registry) с ключом по PK; linger.ms=50, acks=1.
* **Обработка:** Flink (processing‑time, small windows) для обогащения и агрегации без JOIN к БД.
* **Приёмник:** ClickHouse/DWH холдинга (async_insert, батч 1–2 с, ReplacingMergeTree).

**Обоснование соответствия ограничениям:**

* **Без изменения кода монолита:** CDC читает WAL‑логи, не требуя правок в приложении.
* **Без SQL‑нагрузки:** отсутствуют SELECT‑запросы к транзакционным таблицам; нагрузка на БД минимальна (только чтение WAL).
* **Задержка ≤5 с:** суммарная задержка звеньев (WAL→Debezium: 0,2–0,5 с; Kafka: <0,2 с; Flink: 0,1–0,3 с; Sink: 1,0–2,0 с) укладывается в 2–3 с p95.

**Риски и меры:**

* **Раздувание WAL:** мониторинг pg_replication_slots, max_slot_wal_keep_size, heartbeat‑сообщения для малоактивных схем.
* **DDL‑изменения:** регистр миграций для согласования ALTER с владельцем CDC.
* **Таблицы без PK:** REPLICA IDENTITY FULL; крупные транзакции — разбиение на окна.


#**7. Дорожная карта, риски и план перехода**

**Пакеты работ и сроки**

* **Неделя 1–2: Подготовка инфраструктуры и CDC.** Развёртывание реплики PostgreSQL, кластера Kafka (с Schema Registry), Flink, ClickHouse. Настройка replication slot на standby, регистрация DDL‑миграций. Ответственные: SRE, Data Engineer.
* **Неделя 3–4: Пилот CDC и пайплайна.** Настройка Debezium (pgoutput), тестирование передачи событий из схем operational и master_data. Проверка задержки (p95 ≤5 с). Ответственные: Data Engineer, Solution Architect.
* **Неделя 5–6: Разделение BFF и изоляция вебхуков.** Разделение BFF на Web и Courier деплои; внедрение queue‑ingress для вебхуков банка (200 OK + очередь). Тестирование отказоустойчивости. Ответственные: Frontend/Backend Team, SRE.
* **Неделя 7–8: Интеграция с DWH и валидация.** Настройка Sink в DWH холдинга, проверка качества данных и задержки. Валидация соответствия ФЗ‑152 (обезличенные срезы). Ответственные: Data Engineer, ИБ.
* **Неделя 9–12: Dual‑run и переключение.** Параллельная работа старого и нового контуров аналитики; мониторинг расхождений; поэтапное переключение трафика. Ответственные: SRE, Операционный блок.

**Управление рисками и план отката**

* **Риск: потеря событий при сбое CDC.** Меры: DLQ в Kafka, мониторинг pg_replication_slots, автоматическое оповещение при отставании слота. Откат: остановка Debezium, возврат к ручному ETL (если требуется), восстановление слота из бэкапа.
* **Риск: деградация производительности БД из‑за WAL.** Меры: max_slot_wal_keep_size, алертинг по размеру WAL, план очистки. Откат: отключение слота, возврат к исходной конфигурации репликации.
* **Риск: расхождения данных в DWH.** Меры: контрольные суммы, сравнение выборок, журнал расхождений. Откат: возврат к старому контуру аналитики, исправление источника расхождений.
* **Риск: сбои в обработке вебхуков.** Меры: очередь с retry‑политикой, мониторинг очередей, алерты при накоплении сообщений. Откат: возврат к синхронной обработке (временное решение), устранение причины сбоя.

**Критерии успешности и переключение**

* **Метрики качества: задержка доставки событий в DWH ≤5 с (p95); потеря событий = 0%; нагрузка на транзакционную БД от CDC <5% CPU.
* **Шаги переключения:
1. Проверка стабильности пайплайна (72 часа без ошибок).
2. Синхронизация данных (сравнение выборок из DWH и БД).
3. Поэтапное переключение трафика аналитики на новый контур (канареечный деплой).
4. Мониторинг расхождений и задержек в течение 48 часов.
5. Финальная валидация и объявление нового контура основным.

**ИТОГ:**
План трансформации обеспечивает переход к целевой микросервисной архитектуре за 12 месяцев с промежуточным решением для real‑time аналитики (≤5 с) за 3 месяца. Бизнес получает масштабируемость x10, соответствие регуляторным требованиям, снижение рисков простоя и ускорение релизного цикла. Все этапы согласованы с ограничениями по срокам, бюджету и ИБ, а риски минимизированы через dual‑run, мониторинг и план отката.
