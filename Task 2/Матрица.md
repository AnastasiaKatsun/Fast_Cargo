# **2. Отработка возможных возражений** #
**Возражение техлида Fast Cargo:** «Временное решение для DWH создаст риски для стабильности текущих отгрузок и потребует переписывания легаси‑кода».
**Ответ:**

*Решение основано на CDC (Debezium + pgoutput) — читает WAL‑логи без нагрузки на БД и без правок кода монолита.
*Репликация слота вынесена на standby‑реплику PostgreSQL — primary не затрагивается.
*Dual‑run: старый и новый контуры работают параллельно; переключение — поэтапное, с мониторингом расхождений.
*План отката: остановка Debezium, возврат к ручному ETL (если требуется), восстановление слота из бэкапа.

**Возражение отдела ИБ «Продукты с душой»:** «Интеграция CRM нарушает требования ФЗ‑152, так как персональные данные лежат в общем контуре монолита».
**Ответ:**

*ПДн изолированы в PII‑vault (отдельный микросервис с криптозащитой по ГОСТ Р 34.12‑2015).
*В бизнес‑доменах хранятся только subject_id/токены и обезличенные атрибуты.
*CRM получает данные только через API‑шлюз (OIDC + mTLS, скоупы по цели обработки, реестр согласий, аудит обращений).
*В DWH — агрегаты и k‑обезличенные срезы; прямого доступа к транзакционной БД нет.

**Возражение производственного департамента «Продуктов с душой»:** «Поток телематики IoT на 3 000 RPS создаст цунами данных и мгновенно уронит текущую инфраструктуру и СУБД».
**Ответ:**

*Телематика вынесена в отдельный контур: MQTT/EMQX (TLS) → gateway‑нормализация (Protobuf) → Kafka → Flink → ClickHouse/Timescale.
*Отдельный кластер Kafka и БД, отдельный сетевой сегмент — деградация биллинга не влияет на запись геоданных.
*На борту/в приложении курьера — локальный буфер с ретрансляцией после потери связи.
*Запас по пропускной способности: 3 000 RPS — это сотни КБ/с для Kafka; заложен запас ×10 по партициям.
